# CTADMIN EQMU Dashboard and Remediation Experience

**Date:** 2026-08-07  
**Status:** Approved  
**Product:** CTADMIN Technology Administration  

## 1. Overview

Add a CTADMIN-branded, authenticated dashboard experience to the Entitlement Quality Monitor Utility (EQMU). The new interface recreates the capabilities shown in the supplied Appian reference screenshots without depending on Appian for rendering or workflow. It reads and mutates the same EQMU data fabric and rules engine used by the existing API.

The existing operational/API-support dashboard at `/` and its current routes remain unchanged. The new product surface is additive and lives under `/ctadmin`.

## 2. Goals

- Deliver four connected pages: Health Dashboard, Remediation, Finding Detail, and My Findings.
- Render EQMU data directly from the demo application rather than from Appian.
- Preserve the existing dashboard at `/` without changing its behavior or visual structure.
- Make chart segments interactive filters that update compatible KPIs, charts, and tables without a full page reload.
- Provide real, rule-specific remediation for all 13 EQMU rule types.
- Keep the EQMU bearer token and all mutation authority on the server.
- Provide a visible employee persona selector for the My Findings demo.
- Maintain the deterministic rules-engine and JSON audit-trail posture of EQMU.

## 3. Non-goals

- Replacing or redesigning the existing operational/API-support dashboard.
- Depending on Appian SAIL, Appian workflow, or Appian identity.
- Introducing a React/Node build pipeline.
- Adding enterprise SSO, multi-tenant authorization, or production identity governance.
- Automatically choosing an ambiguous compliance repair without a human selection.
- Refactoring unrelated rules, simulator behavior, or public API contracts.

## 4. Architecture

### 4.1 Product boundary

The existing FastAPI/Jinja application will gain a separate authenticated route group, templates, stylesheet, and progressive JavaScript modules:

```text
Existing surface (unchanged)
  /
  /dashboard/*
  /api/*
  resource and workflow APIs

New CTADMIN surface
  /ctadmin/login
  /ctadmin/logout
  /ctadmin/dashboard
  /ctadmin/remediation
  /ctadmin/findings/{violation_id}
  /ctadmin/my-findings
  /ctadmin/api/*
  /ctadmin/actions/*
```

The initial page snapshot is server-rendered. Progressive JavaScript fetches authenticated CTADMIN JSON endpoints for chart filtering, persona changes, pagination, and remediation results. Charts use accessible native SVG generated by the application; no CDN or Node build is required.

### 4.2 Shared application services

Business logic will be separated from route and template code:

- **Dashboard query service:** reads the EQMU JSON store and produces normalized finding rows, target/user context, KPI totals, chart series, and filter metadata.
- **Filter service:** applies status, severity, target type, rule, and persona filters consistently across tables and charts.
- **Repair planner:** converts a current violation and user selection into a validated, explicit mutation plan with before/after values.
- **Repair executor:** applies the plan to an in-memory seed bundle, runs the deterministic engine, reconciles violations, and persists the result only after successful validation/evaluation.
- **Authentication/session service:** validates login credentials, signs sessions, generates CSRF tokens, and enforces route access.

Public API projections and the CTADMIN query service should share focused aggregation/projection helpers when their concepts overlap. The application must not call its own HTTP API internally.

### 4.3 Data flow

```text
Authenticated browser
  -> GET /ctadmin/<page>
  -> server-rendered initial snapshot
  -> GET /ctadmin/api/<dataset>?filters...
  -> interactive SVG charts and table update in place

Repair confirmation
  -> POST /ctadmin/actions/findings/{id}/repair + CSRF token
  -> validate current finding and selected repair
  -> mutate an in-memory bundle
  -> run deterministic EQMU rules engine (no random drift)
  -> verify targeted rule/record finding no longer exists
  -> persist source data and reconciled violations
  -> return before/after result
  -> refresh all affected dashboard state
```

## 5. Authentication and Security

### 5.1 Branded login

`GET /ctadmin/login` renders a CTADMIN-branded login form. `POST /ctadmin/login` validates credentials from configuration and creates a signed session. The login page is the only unauthenticated CTADMIN page.

New configuration settings will cover:

- dashboard username;
- dashboard password or password verifier;
- session-signing secret;
- session lifetime;
- secure-cookie behavior, enabled for HTTPS deployments.

No production password or session secret may be embedded in source. Local development may use explicitly documented environment values.

### 5.2 Session and request protection

- Signed, HTTP-only, SameSite session cookie.
- Secure cookie in deployed HTTPS environments.
- Session rotation on successful login.
- POST-only logout.
- Per-session CSRF token on every state-changing CTADMIN request.
- Constant-time credential comparison or password-hash verification.
- Application-level throttling for repeated login and mutation attempts.
- Safe relative-path redirects only; external return URLs are rejected.
- All `/ctadmin/*` data, page, and action routes require a valid session except login.

The existing `EQM_BEARER_TOKEN` remains server-side. CTADMIN actions invoke shared services directly and do not expose or copy that token into HTML, JavaScript, cookies, or browser storage.

## 7. Navigation and Pages

### 7.1 Shared shell

The authenticated shell contains:

- CTADMIN logo and `Entitlement Quality Monitor` product title;
- navigation links for Dashboard, Remediation, and My Findings;
- current persona indicator when a My Findings persona is active;
- authenticated username and logout action;
- responsive navigation behavior for narrow layouts.

Finding Detail is reached contextually from tables and highlights the originating navigation section.

### 7.2 Health Dashboard — `/ctadmin/dashboard`

The overall health page contains:

1. KPI cards for Total Assignments, Total Findings, Open, High/Critical Severity, and Catalog Findings.
2. Assignment status donut: Clean, Open, Pending Approval, and other active/completed states where present.
3. Findings by severity bar chart.
4. Entitlement catalog coverage donut: With Findings vs Clean.
5. Findings by target type bar chart.
6. Findings by rule bar chart.
7. Filter summary, Clear Filters action, and flagged-record table.

The table columns are Violation, User, Rule, Status, Severity, Target, Recommended Action, and a contextual action link.

Clicking a chart segment toggles its dimension filter. Multiple dimensions combine with AND semantics. Clicking the selected segment again removes that filter. Clear Filters removes every filter. Compatible KPIs, charts, result counts, and the table update in place. A selected dimension remains visually distinguishable and keyboard-toggleable.

### 7.3 Remediation — `/ctadmin/remediation`

The remediation page contains:

- workflow KPI cards: Not Started, In Progress, Complete;
- current filter summary and clear action;
- filter controls for workflow state, severity, rule, target type, and search;
- paginated findings table;
- links to Finding Detail;
- Repair action for every currently repairable finding.

Workflow grouping is explicit:

- **Not Started:** `open`;
- **In Progress:** `pending_approval`, `approved`, and `manual_repair`;
- **Complete:** `resolved` and `rejected`.

Repair opens a rule-specific drawer containing evidence, the proposed mutation, any required selection or editable field, and Cancel/Confirm actions. Opening the drawer does not mutate data.

### 7.4 Finding Detail — `/ctadmin/findings/{violation_id}`

The detail page displays:

- violation ID, rule ID/name, severity, state, and detection timestamp;
- target type/ID and resolved employee context where applicable;
- explanation and structured evidence;
- recommended action and suggested fix;
- the proposed rule-specific repair UI;
- workflow history with actor, time, state transition, note, and repair changes;
- applicable workflow actions.

After a repair, the page shows an outcome panel containing the changed records/fields, before/after values, evaluation outcome, and whether the targeted finding cleared. If the original finding is reconciled to resolved, the detail remains viewable through history rather than returning a not-found page.

### 7.5 My Findings — `/ctadmin/my-findings`

The page has a visible searchable employee persona selector. Selecting an employee stores that persona ID in the authenticated session and refreshes the page scope. The selector does not impersonate authentication; it is explicitly a demo perspective control.

The selected persona sees findings that:

1. directly target the employee;
2. target one of the employee's active assignments;
3. target an entitlement held through an active assignment.

The page contains Open, Pending Approval, and Resolved KPI cards; severity and rule charts; filter controls; a result table; links to detail; and the same rule-specific repair drawer used by Remediation. Repairs immediately affect My Findings and the administrative pages because all read from the same store.

## 8. Rule-Specific Remediation

Every repair requires a preview and confirmation. The planner rejects a finding that is no longer current or whose target/evidence no longer matches the stored data.

| Rule | Finding | Repair behavior |
|---|---|---|
| ENT-Q-01 | PBL completeness | Editable PBL description initialized from the suggested fix; save the confirmed description. |
| ENT-Q-02 | PBL template match | Editable PBL description initialized with tier-specific guidance; validate the confirmed text by re-running the rule. |
| ENT-Q-03 | Tier vs role coherence | Remove the forbidden roles identified by evidence; preview the resulting acceptable-role list. |
| ENT-Q-04 | Division-resource coherence | For HR/developer conflict, remove `developer`; for Legal/Compliance Tier-1 on production, downgrade to Tier 2. Preview the exact branch selected from current evidence. |
| TOX-01 | Maker-checker conflict | User chooses left or right SOD side; revoke active assignments granting the selected side for the affected employee. |
| TOX-02 | Dev + Prod-Admin same application | User chooses developer or operations side; revoke the affected employee's assignments to entitlements listed on that side of the evidence. |
| TOX-03 | Tier-1 in 3+ divisions | User selects Tier-1 assignments/divisions to revoke; planner requires the proposed remainder to span no more than two divisions. |
| HR-01 | Role mismatch | Revoke the targeted assignment. |
| HR-02 | Division mismatch | Revoke the targeted assignment. |
| HR-03 | Legacy entitlement after role change | Revoke the targeted assignment after explicit manager-confirmation acknowledgement. |
| HR-04 | Terminated user holds active assignment | Revoke the targeted assignment. |
| CMDB-01 | Orphan entitlement | User selects a valid CMDB resource; add the resource ID to the entitlement's links and maintain the reciprocal resource link where applicable. |
| CMDB-02 | Tier inconsistency on critical resource | Apply the suggested access tier, normally Tier 2, after previewing the tier change. |

Assignment revocation preserves the assignment record and sets `active` to `false`, matching the existing API behavior.

### 8.1 Workflow audit

For a successful repair, the executor appends auditable history containing:

- authenticated CTADMIN actor;
- timestamp;
- originating violation and rule;
- selected action/choice;
- affected record IDs;
- before/after values;
- evaluation outcome;
- any acknowledgement note.

The workflow follows legal EQMU transitions. A direct repair uses the appropriate `manual_repair`/`resolved` path or a dedicated, validated service transition sequence rather than silently overwriting workflow state.

### 8.2 Success criteria

A repair is successful only if the same rule/target combination is absent from the new active violations after evaluation. Violation IDs alone are not used for this check because reconciliation may regenerate or preserve identifiers. If the condition remains, no success claim is shown; the UI displays the remaining reason and preserves the user's input where possible.

## 9. Consistency and Persistence

Repairs are serialized with an application-level asynchronous lock. The executor will:

1. read the current source records and violation;
2. validate the submitted choice against current evidence;
3. build a complete in-memory candidate bundle;
4. apply the candidate repair;
5. run the rules engine with current violations for reconciliation;
6. confirm that models validate and the targeted condition clears;
7. persist the affected data and reconciled violations with recoverable/atomic file-writing behavior;
8. return the repair receipt.

If validation, evaluation, or persistence preparation fails, the source files remain unchanged. Persistence failures must surface a clear error and preserve recoverability; implementation must not report success from a partial write.

## 10. Error and Empty States

- Invalid or expired session: redirect page requests to login; JSON/action requests return an authentication error.
- CSRF failure: reject without mutation and show a retryable session message.
- Stale finding: explain that the record changed and refresh the current finding state.
- Invalid repair choice: identify the invalid field/choice without changing data.
- Finding remains after evaluation: show the remaining evidence/reason and do not label the repair complete.
- No findings: show a positive clean-state card and keep persona/filter controls usable.
- No filter results: show a zero-result state with Clear Filters.
- Missing persona: prompt the presenter to select an employee.
- Data read/validation failure: show a non-sensitive error with retry; log diagnostic detail server-side.
